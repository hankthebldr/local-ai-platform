# Enclave 1.1 → 1.2 — UI / UX User Flows

**Companion to:** `2026-05-16-roadmap-spec.md` + `2026-05-16-implementation-plan.md`
**Date:** 2026-05-16

Detailed user flows for every shipped feature in the 1.1 → 1.2 roadmap, with
ASCII mockups in the Cortex Console visual language and explicit integration
points into the existing dashboard. The principle throughout: **extend
existing surfaces; do not build parallel ones.**

## 1. Visual language reference

Everything below uses these existing primitives. New UI must reuse them.

| Pattern | CSS / file ref | When to use |
|---------|---------------|-------------|
| Panel with scan-line accent | `.panel`, corners `.corner-tr/.corner-bl` | Any content container |
| Section label with pip | `.panel-label` | Title above any panel |
| Card grid (auto-fill 280–340px) | `.inv-grid`, `.wfi-grid` | Listing items |
| Card with header + desc + meta + tags + actions | `.inv-card`, `.wfi-card` | Items in a grid |
| Status pill | `.tag` + semantic color | INSTALLED / AVAILABLE / RUNNING |
| Admin modal shell | `.admin-modal` + `.admin-modal-card` | Any create/edit/inspect dialog |
| Action button | `.action-btn` (cyan = secondary, accent = primary) | Card row, toolbar |
| Drop zone | `.doc-drop-zone` | Empty states inviting input |
| Markdown code block | `.md-code` | Skill body, agent prompts, eval output |
| Tracking-caps label | `letter-spacing: var(--tracking-caps)` | Section dividers, badges |

**Color rules:**
- `--accent: #00CC66` (Cortex Green) — CTAs, success, primary actions
- `--accent-2: #5EB3FF` (Cool Blue) — navigation, info, secondary
- `--warn` — needs attention, not failure
- `--danger` — failure, destructive confirmations
- Status pip glow: `0 0 10px <color>40, 0 0 2px <color>80`

## 2. Citation rail on chat responses (Workstream A)

**Entry point:** under every assistant message in the Composer's chat dock
(bottom of `tab-dashboard`) and in any chat surface that consumes
`/v1/chat/completions`.

**User goal:** "Show me what shaped this answer so I can trust it or audit it."

### Flow

1. User sends a message in the chat dock.
2. Response streams in normally.
3. After the final SSE chunk lands, the rail appears below the message —
   one fetch to `/api/provenance/response/{id}` populates it.
4. Collapsed by default. One click expands inline; second click collapses.

### Mockup (collapsed)

```
┌─ assistant ───────────────────────────────────────────────────────┐
│ Yes, you can switch the embedding model. Update                   │
│ `EMBED_MODEL` in your `.env` and re-run the indexer…              │
│                                                                    │
│ shaped by:  ◆ 2 skills  ▣ 3 chunks  ✦ 1 tool         [details ▾]  │
└────────────────────────────────────────────────────────────────────┘
                                          ↑ 0.68rem, --text-muted
```

### Mockup (expanded)

```
┌─ assistant ───────────────────────────────────────────────────────┐
│ Yes, you can switch the embedding model. …                         │
│                                                                    │
│ shaped by:  ◆ 2 skills  ▣ 3 chunks  ✦ 1 tool         [details ▴]  │
│                                                                    │
│ ┌─ Skills (2) ──────────────────────────────────────────────────┐ │
│ │  ◆ code::read-before-edit                            always-on│ │
│ │  ◆ code::match-existing-style                        always-on│ │
│ ├─ Retrieved chunks (3) ─────────────────────────────────────── │ │
│ │  ▣ 87% │ api/services/embedding_service.py:42-78  ↗            │ │
│ │  ▣ 74% │ docs/HUGGINGFACE_SETUP.md                ↗            │ │
│ │  ▣ 61% │ MODELS.md                                ↗            │ │
│ ├─ Tools (1) ─────────────────────────────────────────────────── │ │
│ │  ✦ 340ms │ rag::search("embedding model switch")               │ │
│ └────────────────────────────────────────────────────────────── │ │
└────────────────────────────────────────────────────────────────────┘
```

### Integration

- Render hooks into the existing chat message renderer (search for the
  function that appends `.chat-message` nodes).
- Each row is a `<button>` (a11y); click navigates:
  - chunk → opens the Context tab filtered to that doc, scrolled to line
  - skill name → opens the admin Skills modal scrolled to that skill
  - tool call → opens an inline drawer with full args + result + latency
- Truncation: >10 rows per type → top 5 + `[5 more ▾]` inline expand.
- Empty state (rare): `shaped by: no sources tracked for this response`
  (renders only if `ENABLE_PROVENANCE` is on but the response had no edges).

### States

| State | Visible UI |
|-------|-----------|
| Loading (post-stream) | `[shaped by: …]` skeleton, 200 ms max |
| Loaded | Rail with counts |
| Provenance disabled | Rail hidden entirely |
| Error fetching | Silent; rail hidden (don't alarm the user over an analytics fetch) |

### Edge cases

- Streamed response where SSE drops mid-flight: emit a `response_complete`
  marker server-side; rail only renders after that marker.
- Re-renders (e.g., conversation reload): rail refetches; cache lives in
  `localStorage.provenance_cache_<conversation_id>` for ≤24h.

## 6. Ollama-not-running banner (Workstream C)

**Entry point:** Server-wide. Any 503 from Ollama via the middleware.

**User goal:** "Tell me what's wrong and let me fix it without leaving."

### Banner

Renders at the top of every tab when Ollama is unreachable. Styled with
`--warn` border, accent button.

```
┌──────────────────────────────────────────────────────────────────────┐
│ ⚠ Ollama isn't running. Most features will be unavailable.           │
│                                       [Start Ollama]   [How to fix?] │
└──────────────────────────────────────────────────────────────────────┘
```

### Flow

1. Background `/api/healthz` poll every 10s. If Ollama section reports
   unreachable, dispatch a global "ollama-down" event.
2. Banner renders with two actions:
   - **Start Ollama**: calls `/api/setup/start-ollama` (new endpoint; runs
     `ollama serve` for DMG users, `docker compose start ollama` for Docker
     users — detection via env var the install path sets).
   - **How to fix?**: opens an admin modal with paste-able commands per
     install path.
3. On success poll, banner animates out.

### Banner template

```html
<div id="ollama-down-banner" hidden class="panel"
     style="border-color:var(--warn);">
  <strong>⚠ Ollama isn't running.</strong>
  Most features will be unavailable.
  <button class="action-btn primary" onclick="Doctor.startOllama()">
    Start Ollama
  </button>
  <button class="action-btn" onclick="Doctor.showFix()">
    How to fix?
  </button>
</div>
```

### Edge cases

- Already running but unreachable (port conflict): banner copy adapts to
  "Ollama is running but on a different port" + show detected port.
- Auto-start fails: banner stays, with new copy "Couldn't start automatically.
  Run `ollama serve` in a terminal."

## 10. Response receipts (Workstream C)

**Entry point:** Under every assistant message, **above** the citation rail.

**User goal:** "Remind me what this is saving me."

```
┌─ assistant ───────────────────────────────────────────────────────┐
│ ... answer text ...                                                │
│                                                                    │
│ 247 tokens · 3.2s · qwen2.5:14b · ≈ $0.012 on GPT-4               │
│ shaped by:  ◆ 2 skills  ▣ 3 chunks  ✦ 1 tool         [details ▾]  │
└────────────────────────────────────────────────────────────────────┘
```

### Implementation

- Tokens + time pulled from `/v1/chat/completions` usage data (already
  reported).
- Cost-equivalent: a static table `cost_per_million_tokens.py` with the
  current API prices. Output = input_tokens × table[gpt-4] + output_tokens ×
  table[gpt-4].
- "GPT-4" comparison hardcoded for 1.2; M2 lets the user pick the comparison
  model.
- Toggle in Settings → Display: "Show cost comparison." Default on for new
  users.

### Flow — watched folder

1. Click "+ Watch folder" → native file picker.
2. Picked → POST `/api/documents/watch {path: …}`.
3. Backend uses `watchdog` to subscribe; initial index runs as a background
   job with a progress pill on the row.
4. Future changes → debounced incremental upsert (file → chunk → embed).
5. Removed → POST `/api/documents/watch/{id}/unwatch`. Indexed docs stay
   unless user also clicks "Remove indexed docs."

1. Click "Run audit" → backend runs the doc audit (using provenance edges
   where source_type=doc or rag_chunk).
2. Results render in collapsible groups by issue type.
3. "Review" → drills into a list with one-click archive per row.
4. "Archive all" → confirmation modal, then bulk action.

- Doc audit: new endpoint `GET /api/documents/audit?since=90d` reads
  provenance + document metadata.

## 18. Cross-cutting state library

A reusable set of states every flow above adopts. Document these once so the
implementation team isn't reinventing.

### Loading

- **Inline skeleton:** for content under 200 ms. Single line, dim, animated
  fade.
- **Spinner:** for 200 ms – 2 s. `.action-btn` shows a spinner glyph.
- **Progress bar:** for >2 s, where progress is known (model pull, doc
  indexing, re-embed). Uses existing `.progress-bar` from setup.html.
- **Indeterminate scan:** for >2 s with unknown end (workflow runs). Uses
  the existing scan-line animation.

### Empty

- **Drop-zone style:** for "user can add content here" (watched folders, new
  project). Dashed border, centered glyph + text.
- **Centered text only:** for "nothing here, nothing to do" (project with no
  conversations).
- **Centered text + CTA:** for "nothing here yet, do this." Reused: model
  empty state in Inventory.

### Error

- **Inline banner:** for recoverable errors at the page level (Ollama down).
  `--warn` border for warnings, `--danger` for failures.
- **Toast:** for transient failures (copy succeeded/failed, save failed).
  4-second timeout.
- **Modal:** for hard failures requiring user input (irrecoverable workflow
  state, schema migration needed).

### Success

- **Toast:** for "your action worked." 2.5-second timeout. Cyan border.
- **Inline confirm:** for "action complete on this card" (e.g., copy to
  clipboard). Replaces the action label with `✓ copied` for 1.5 s, then
  reverts.
